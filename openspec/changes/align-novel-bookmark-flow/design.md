# Design

## Context

当前图片收藏和小说收藏分别实现了更新检查、分页、下载跳过和启动校验。小说流程已经能生成并校验 EPUB，但私密收藏请求失败可能被判定为未变化，404 小说没有跨轮询状态，且一致性查询失败不会进入轮次结果。相关入口集中在 `v2.0/novel.py`、`v2.0/bookmark.py`、`v2.0/scheduler.py` 和 `v2.0/log_record.py`。

## Goals / Non-Goals

**Goals:**

- 让更新检查、详情处理和轮次汇总拥有明确的成功、跳过、失败和不可访问状态。
- 使明确 404 的小说在跨轮询范围内幂等处理，同时保留历史归档。
- 让一致性检查失败和分页失败可被调度器与日志准确观察。
- 复用现有配置、数据库连接池、Loguru 和测试方式，不改变 EPUB 产物格式。

**Non-Goals:**

- 不把小说下载改造成与图片相同的线程池模型；EPUB 内嵌资源仍按小说构建器的顺序处理。
- 不删除或重命名已有数据库记录、本地图片或 EPUB。
- 不改变 Pixiv API、登录流程或收藏目录的业务含义。

## Decisions

### 1. 使用三态更新检查结果

小说更新检查返回 `changed`、`unchanged` 或 `error` 三种内部状态。公开或启用的私密收藏任一请求失败都返回 `error`；只有所有请求成功且没有发现新作品时才返回 `unchanged`。图片流程保留现有行为，但在轮次汇总层采用同样的失败语义。

备选方案是继续使用布尔值并用额外全局字段传递错误，这会让调用方无法区分“空收藏”和“请求失败”，因此不采用。

### 2. 用独立不可访问表保存小说 404 状态

新增 `novel_unavailable` 表，以 `nid` 为主键保存状态、原因和最近确认时间。详情接口明确返回 404 时写入或更新该表；更新检查把该表中的 ID 视为已处理项。已有 `novel` 记录和本地 EPUB 不做删除或覆盖。

独立表避免向现有 `novel` 表插入缺少标题、作者等详情字段的伪记录，也避免把现有非空列改成可空。管理员可删除对应状态记录以便手动重新检查恢复的作品。

### 3. 统一轮次统计，而不是统一下载实现

保留 `Novel` 的 EPUB 构建和 `Bookmark` 的图片线程池，各自维护本地下载细节；两者都使用稳定的事件前缀和统一的汇总字段：成功、已有归档跳过、404 跳过、详情失败、分页失败、一致性失败。数据库查询异常使用独立失败字段，不能返回空列表伪装成无记录。

### 4. 让 404 在重试层之前结束

小说详情请求先识别明确的 404，再进入通用 JSON/网络错误处理。404 只记录一次删除提示；其他错误继续使用有限重试并记录尝试次数和错误类别。图片下载沿用现有限流机制，不把小说内嵌图片请求直接改成图片收藏的线程池。

### 5. 将小说已有记录跳过提升为可观察事件

`SKIP_DB_EXISTS_NOVEL` 从静默调试日志提升为稳定的跳过事件，加入控制台聚合和文件日志；最终汇总仍提供数量，避免每个作品的普通成功日志造成“重复下载”的误解。

## Risks / Trade-offs

- [不可访问状态可能过期] → 404 状态提供明确的数据库记录，允许管理员删除后重新检查；后续可增加配置化过期时间而不改变主流程。
- [新增表的部署遗漏] → 在小说流程启动时使用幂等建表，并在 SQL 文档中提供创建语句；建表失败直接标记本轮不完整。
- [图片和小说仍有并发差异] → 规格统一可观察状态和错误语义，不强制统一下载并发，避免 EPUB 构建器出现共享资源问题。
- [多进程日志聚合状态独立] → 稳定事件同时写入文件和轮次汇总，控制台聚合仅作为展示优化，不作为统计来源。

## Migration Plan

1. 发布代码和 `novel_unavailable` 建表逻辑；首次启动自动创建表，不修改已有归档数据。
2. 部署后观察一轮公开、私密、404 和一致性检查日志，确认汇总字段与现有监控兼容。
3. 若需回滚，停用新状态写入并保留该表；原有 `novel` 表和 EPUB 文件可继续由旧版本读取。
